# rsolv-host

The trusted client that RSOLV's reusable GitHub Actions workflows run on your runner, and the
core library it shares with the RSOLV platform. Apache-2.0.

## Status

The shared core library, `rsolv_core/`, and the host client's source, `rsolv_host/`, are here.
The host client has no release yet: its attested release binaries and the sandbox image it
runs land in later changes. Until they do, the last point of the trust model below (pinned,
attested binaries) is the design those changes must meet, not something you can verify today.

## Trust model

- **What runs where.** RSOLV's AI model runs on the RSOLV platform. Its tool calls (read a file,
  run the tests) run on your runner, inside a sandbox container that `rsolv-host` starts: no
  runner tokens, no Docker socket, a non-root user, only a copy of your repository mounted, and
  network access only to GitHub and package registries through a filtering proxy.
- **Roles.** The scan role is run-wide: its run token covers one workflow run, not one issue.
  The work, verify and publish roles are issue-bound: each run token covers one workflow run,
  one issue and one role.
- **What `rsolv-host` holds.** A short-lived RSOLV run token, obtained from GitHub Actions OIDC
  (no RSOLV secret is configured anywhere), and, in the scan and publish jobs only, the job's own
  `GITHUB_TOKEN`. Neither ever enters the sandbox.
- **What it trusts.** Nothing the sandbox returns: tool output, the patch and test reports are
  size-capped, untrusted bytes. After a sandbox starts, `rsolv-host` never runs git or opens a
  path in the mounted tree.
- **What it writes.**
  - In the scan job: GitHub issues and their labels. The titles and bodies are written inside
    the sandbox, and no signed decision covers them; `rsolv-host` bounds them with fixed caps on
    the number of issues and their size, and an allowlist of labels.
  - In the publish job: only what a decision signed by the platform (Ed25519) allows: two
    commits (the failing test, then the fix), one branch, one pull request, and the labels and
    comments the decision names.
- **How you know what runs.** RSOLV's workflows will pin each release binary by SHA-256, and the
  platform only accepts workflow commits on its allowlist. Every release will be built in this
  repository by GitHub-hosted runners and carry a build-provenance attestation:
  `gh attestation verify <binary> --repo RSOLV-dev/rsolv-host`, plus the flags in
  [docs/RELEASE-RUNBOOK.md](docs/RELEASE-RUNBOOK.md#verifying-a-release-anyone) that pin the
  workflow, tag and commit.

## Protocol

The relay and token-exchange messages between `rsolv-host` and the RSOLV platform carry a
`protocol_version`. `rsolv-host` is the only supported client. The protocol may change in any
release; knowing it grants no access, because every request is bound to a run token issued for
one workflow run and role (and, for every role but scan, one issue).

Verify (RFC-150 §5): `GET …/touched-paths` → `POST …/base-facts` (`RsolvCore.BaseFacts`) →
`GET …/verify-plan` (`RsolvCore.VerifyPlan`) and `GET …/post-images` → `POST …/verification`.
Canonicalization (`RsolvCore.Patch`, `RsolvCore.Canonicalize`) runs on the platform; its golden
vectors (`rsolv_core/test/vectors/patch.json`) are generated by git and run in both repositories.

## Exit codes

`rsolv-host` exits with one of these codes. They are a stable interface; changing one is a
breaking change. `rsolv-work.yml` retries once on 3.

| Code | Meaning | Annotation | Workflow behaviour |
|---|---|---|---|
| 0 | A model or verify outcome was reached (any of them) | `::notice::` for a false positive, a fix that failed verification, or a rejected fix | none |
| 1 | Bug in the host client | `::error title=RSOLV host client bug::`, asking for an issue on `RSOLV-dev/rsolv-host` with the run URL | none |
| 2 | Configuration, or something the customer can fix | `::error title=RSOLV configuration::` naming the fix (for example "Grant `id-token: write`") | none |
| 3 | Transient platform or network failure | `::error title=RSOLV transient failure::` | `rsolv-work.yml` retries once, only on 3 |
| 4 | Sandbox or runner infrastructure | `::error title=RSOLV sandbox setup::` naming the failed step | none |

What falls in each class:

- **1, host bug:** an exception, exit or throw inside `rsolv-host`, or a process it depends on
  ending abnormally. The release always exits; it never hangs until the job timeout.
- **2, configuration:** missing permissions or variables, a platform or GitHub refusal (4xx, or
  any redirect, which is never followed), a signed decision refused or expired, a base whose files or
  `.gitattributes` differ from what the decision signs, a target branch
  that no longer contains the scanned commit, a fix branch or pull request that already holds
  something else, a fix touching `.github/`, a verify checkout that isn't the scanned commit,
  base files or touched paths too many or too large to verify, a verify plan this host refuses, an issue already published
  or rejected, the project's tests running past their time limit in the verify job, and a
  base commit too slow to read with git on the runner.
- **3, transient:** network failures, 429 and 5xx, a run token that expired or a token keeper
  that stopped answering, the platform or GitHub breaking the protocol (a malformed answer or
  event stream, or a touched path that isn't a safe repository path), a session past its time
  budget, and a token exchange whose answer was lost (`409 already_exchanged` on the retry).
- **4, sandbox:** Docker or a sandbox setup step failing, the run-token hand-off file not
  writable, the sandbox breaking its CLI contract: a malformed or oversized frame, more frames or
  issues than allowed, an issue it didn't file, a malformed patch. The scanner's stdout and stderr
  share the frame channel, so `rsolv-sandbox scan` must write nothing to stderr. In the verify
  job: git failing to read the base commit, and a verify error (a sandbox failure, or the
  project's install failing without the fix), which a new attempt may retry.

The `work` role writes the step outputs `outcome` and `has_patch` (`true` or `false`), and a
job-summary row. `outcome` is one of:

- `mitigated`: a fix was produced and uploaded;
- `mitigation_failed`: the vulnerability was confirmed but no usable fix was produced;
- `false_positive`: VALIDATE found the finding is not a vulnerability;
- `not_validated`: VALIDATE could not confirm the vulnerability;
- `validated`: VALIDATE confirmed it, then the job failed (non-zero exit) before MITIGATE
  reported an outcome.

The `verify` role (`verify --issue N`) writes the same outputs (`has_patch` is always
`false`), with `outcome` one of:

- `verified`: RED failed and GREEN passed as the platform requires;
- `verify_failed`: the platform judged RED and GREEN and refused the fix;
- `rejected`: the platform's policy rejected the fix, or it has no runnable RED test.

Annotations and summaries are fixed text plus host-controlled values; text from the sandbox or
an error response never reaches them.

## Layout

- `rsolv_core/`: what the platform and the host must agree on byte for byte: the relay
  protocol types, canonical JSON (RFC 8785, for the subset RSOLV signs, which has no floats),
  the change set and the signed decision envelope. It depends on nothing in the platform.
- `rsolv_host/`: the host client, packaged with Burrito as a self-contained Linux binary
  (not yet released).

## Building the binary

The binary wraps a glibc ERTS that we build ourselves from pinned sources
(`rsolv_host/scripts/erts-inputs.env`), never Burrito's downloaded musl ERTS. `erts.lock`
pins each architecture's ERTS tarball by SHA-256, and the release refuses any tarball that
doesn't match (`RsolvHost.Release.verify_erts/2`). It checks a copy in a new private
directory, and Burrito unpacks that copy, so the tarball can't change between check and use. Each architecture builds natively on its
own machine; nothing runs under emulation. The ERTS build's apt packages all come from a
fixed Ubuntu archive snapshot. The release is compiled with that same OTP (the ERTS tarball is
a full OTP release, checked against `erts.lock` before use), plus Elixir, Hex and rebar3 files
pinned by SHA-256 in `scripts/install-toolchain.sh`, so every `.beam` in the binary comes from
a pinned input.

Burrito's launcher is patched at build time (`rsolv_host/patches/burrito-launcher-env.patch`,
applied and hash-checked by `RsolvHost.Release.PatchLauncher`). Before it starts `erlexec`,
the patched launcher refuses any `ERL_*FLAGS`, `ERL_LIBS` or `ERL_COMPILER_OPTIONS` (exit 2,
configuration), and removes every `LD_*` variable and `EMU`, so the caller's environment can't
add VM flags, load a library into the VM or pick another emulator. `scripts/smoke.sh` tries
each of these against the real binary.

```bash
cd rsolv_host
scripts/install-zig.sh "$HOME/zig-0.16.0" && export PATH="$HOME/zig-0.16.0:$PATH"  # Burrito 1.6.0 needs exactly 0.16.0
scripts/build-erts.sh "$(uname -m)" erts                # needs Docker; prints the tarball's SHA-256
tc="$HOME/rsolv-toolchain"                                # OTP from the ERTS tarball, Elixir, Hex, rebar3
scripts/install-toolchain.sh erts "$tc" && export PATH="$tc/otp/bin:$tc/elixir/bin:$PATH" MIX_HOME="$tc/mix"
MIX_ENV=prod BURRITO_TARGET="linux_$(uname -m)" mix deps.get --check-locked
MIX_ENV=prod BURRITO_TARGET="linux_$(uname -m)" mix release
scripts/smoke.sh "burrito_out/rsolv_host_linux_$(uname -m)" --online
```

The ERTS build is reproducible: the same inputs give the same tarball, byte for byte, so a
rebuild can be checked against `erts.lock`. The first run of the binary extracts it into
`$RSOLV_HOST_INSTALL_DIR`, which must be under `$RUNNER_TEMP`. Two first runs against the same
directory race (the loser exits 1, and the extracted tree stays intact), so the workflows must run
the binary once, serially, before anything else.
